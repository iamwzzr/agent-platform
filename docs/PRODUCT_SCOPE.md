# Agent Platform 产品合同

## 一句话定义

本项目帮助求职者输入职位描述和候选人证据资料，生成带来源引用的结构化求职申请材料；每项候选人事实都必须能够追溯到输入证据，没有证据时必须标记为缺口，不得编造。

## 为什么创建这个项目

普通 LLM 聊天可以快速生成文案，但容易遗漏职位要求、夸大候选人经历、丢失引用，并且在调用失败后难以恢复。本项目把求职材料生成限制成一条有边界、可观察、可校验的 Agent workflow：

```text
职位描述 + 候选人证据文档
→ 提取职位要求
→ 检索相关证据
→ 起草申请材料
→ 校验每项事实及引用
→ 有界修订或明确失败
→ Artifact 落库
```

它不是一个什么都能聊的机器人，而是一个只完成上述业务闭环的求职证据 Agent。

## 目标用户

- 正在准备特定职位申请材料的求职者。
- 用户愿意提供真实简历、项目记录、证书或作品集作为证据。
- 用户需要查看每项生成内容来自哪里，并在投递前进行人工确认。

## 输入合同

| 输入 | 是否必需 | 说明 |
| --- | --- | --- |
| `job_description` | 是 | 一份具体职位描述，包含职责、必备技能和加分项。 |
| `evidence_documents` | 是 | 候选人的简历、项目记录、证书、作品集或其他可验证资料。 |
| `preferences` | 否 | 语言、语气、长度和目标材料类型等偏好，不得改变证据事实。 |
| `workspace_id` | 是 | 限定本次请求能够访问的数据范围，禁止跨 workspace 检索。 |

空职位描述、不可访问的文档 ID、错误 workspace 或非法字段必须在运行开始前被拒绝。

## 输出合同

一次成功 Run 生成一个 `ApplicationArtifact`，至少包含：

| 字段 | 含义 |
| --- | --- |
| `requirements` | 从职位描述提取出的职位要求。 |
| `claims` | 准备写入申请材料的候选人事实；每项都必须带有效引用。 |
| `resume_bullets` | 针对职位调整后的简历要点，只能使用已验证的 claims。 |
| `cover_letter` | 可选的求职信草稿，只能使用已验证的 claims。 |
| `gaps` | 职位要求存在、但候选人资料中没有足够证据支持的缺口。 |
| `citations` | 指向来源文档与片段的引用；RAG 阶段统一为 `document_id + chunk_id`。 |
| `run_id` | 关联本次执行过程、事件、错误与恢复记录。 |

只有通过引用校验的 Artifact 才能以成功状态落库。

## 证据与生成规则

1. 每一项对外陈述的候选人事实必须至少关联一个有效引用。
2. 引用必须属于当前 workspace，并且来源片段确实支持对应事实。
3. 相邻技能不能自动互相证明，例如会 C 语言不能证明会 Python。
4. 模型可以改写表达，但不能新增公司、项目、职责、技能、数字或工作年限。
5. 没有证据时必须生成 `gap`，不得为了文案完整而补写事实。
6. “可能具备迁移能力”只能作为待核实建议，不能写成已经掌握的候选人事实。
7. 用户偏好只能改变语言和表达形式，不能覆盖证据规则。

## Case 1：有证据

- 职位要求：具备 Python 后端开发能力，能够使用 FastAPI 开发 HTTP API 并编写自动测试。
- 候选人证据：候选人在 `backend/app/main.py` 中使用 Python 和 FastAPI 实现了 liveness API，并在 `backend/tests/test_health.py` 中编写了响应状态码与 JSON 内容的自动测试；对应代码提交为 `8019397`。
- 允许生成：候选人使用 Python 和 FastAPI 实现过可运行的健康检查接口，并为接口编写过自动测试。
- 必须引用：`backend/app/main.py`、`backend/tests/test_health.py` 和代码提交 `8019397`。
- 禁止夸大：不能把一次最小项目实践写成“精通 Python”或多年生产经验。

## Case 2：无证据

- 职位要求：具备 Python 后端开发能力。
- 候选人证据：本案例输入的候选人资料只证明其完成过 C 语言项目，没有提供 Python 代码、项目、课程或工作经历。
- 预期结果：输出证据缺口“缺少 Python 后端开发能力的可验证证据”，不生成对应的经历描述，并提示候选人补充 Python 项目或代码证据。
- 禁止生成：不得因为候选人会 C 语言就推断其会 Python；不得声称候选人“熟练/精通 Python”；不得编造不存在的 Python 项目、公司、职责或年限。

> 当前案例暂时使用文件路径和 Git commit 作为引用。阶段 3 实现 RAG 后，系统引用统一使用可查询的 `document_id` 与 `chunk_id`。

## 三类核心失败

| 失败 | 系统行为 | 不允许的行为 |
| --- | --- | --- |
| 请求非法 | 返回明确的 4xx；不创建 Run，不生成 Artifact。 | 不能让非法输入进入 LLM 或数据库工作流。 |
| Provider 失败 | 记录 RunEvent；仅对临时错误进行有界重试；保留 checkpoint，最终成功或明确失败。 | 不能无限重试、重复付费或伪造成功结果。 |
| 引用校验失败 | Artifact 不以成功状态落库；进入有上限的 revise，耗尽次数后标记失败并保留原因。 | 不能绕过 validator 保存无来源事实。 |

## 非目标

- 不做与职位申请材料无关的通用聊天机器人。
- 不自动搜索职位、登录招聘网站或替用户投递申请。
- 不替招聘方评分候选人或作出录用、淘汰决定。
- 不从技能相似性、常识或模型记忆中补写候选人经历。
- 不保证生成材料一定获得面试或录用；最终内容必须由用户审核。

## 固定质量标准

| 指标 | 阶段目标 |
| --- | --- |
| 引用覆盖率 | Artifact 中候选人事实带至少一个引用的比例必须为 100%。 |
| 引用有效率 | 引用能够定位到当前 workspace 中真实存在且支持该事实的来源，固定评测中必须为 100%。 |
| 无证据行为 | 固定无证据 case 必须输出 gap，unsupported claim 数量必须为 0。 |
| 需求覆盖 | 每项职位要求必须被标记为 `supported` 或 `gap`，不能静默遗漏。 |
| 有界执行 | revise 和 Provider retry 都必须有明确上限，不允许无限循环。 |
| 幂等与恢复 | 相同幂等键不得重复创建 Run 或重复付费；恢复后不重做已完成节点。 |
| 离线可测试 | 默认自动测试不访问真实 LLM；固定 Mock 结果必须可重复。 |

## 完成定义

当用户提交一次合法请求后，系统能够：

1. 在当前 workspace 中保存并读取 Job 与证据文档。
2. 检索可追溯的证据片段。
3. 通过 LangGraph 执行提取、检索、起草、校验和有界修订。
4. 对合法事实生成引用，对无证据要求生成 gap。
5. 记录 Run、RunEvent、错误、checkpoint 和最终 Artifact。
6. 使用固定评测阻止检索、引用或 Prompt 质量回退。
7. 在 React 操作台展示运行状态、材料、引用、缺口和恢复入口。
